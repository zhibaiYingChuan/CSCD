## 三、关键发现

### 1. 协议在代码审查任务上**未带来质量提升**

T2 中 A 组（直答）已经发现了全部 5 个预埋缺陷，且给出了完整的修复代码。B 组和 C 组在协议框架下同样发现了全部缺陷，但输出被协议元描述挤占，实际有效内容反而更少。

**结论：对于代码审查这种 AI 擅长的结构化任务，CSCD 协议没有带来额外价值。**

### 2. 协议在歧义需求上**价值最大**

T4 中 A 组（直答）直接给出了假设性的完整方案，完全没有识别需求中的模糊点。而 C 组（多轮）通过事实/假设/噪音分类，明确标注了哪些是假设、哪些需要确认，行为上更接近"先澄清再设计"。

**结论：对于需求澄清、方案设计等开放任务，CSCD 协议的防过早完成能力显著优于直答。**

### 3. 单轮协议（B 组）**存在空结果风险**

T4-B 组返回 0 Token，因为模型在单轮中未能正确输出四阶标记，而协议严格的校验逻辑导致空结果输出。这在实际使用中是不可接受的。

**结论：单轮协议需要增加 fallback 策略（如校验失败时输出原始结果）。**

### 4. 多轮递归（C 组）Token 开销显著

C 组总输出 16,384 Token，是 A 组（6,396）的 2.56 倍。在复杂推理和需求澄清任务上，额外 Token 开销带来了质量提升；但在代码审查上，额外开销没有带来质量提升。

**结论：协议应按任务类型差异化启用，而非全量使用。**

## 四、总结

| 指标 | A 组（直答） | B 组（单轮） | C 组（多轮） |
|------|------------|------------|------------|
| 总输出 Token | 6,396 | 6,144 | 16,384 |
| 空结果次数 | 0 | 1（T4） | 0 |
| 歧义需求处理 | ❌ 直接假设 | ❌ 失败 | ✅ 分类标注 |
| 代码审查完整性 | ✅ 全部发现 | ✅ 全部发现 | ✅ 全部发现 |
| 复杂推理深度 | 全面但无重点 | 结构完整但稀释 | 深度最优 |
| 产品设计防刷覆盖 | ❌ 缺失 | ✅ 覆盖 | ✅ 覆盖 |
| 协议开销收益比 | 基线 | 低（多数任务无增益） | 高（歧义任务显著） |

### 建议

1. **CSCD 协议不适用于所有任务**——代码审查、明确指令类任务直答已足够
2. **歧义需求、方案设计、复杂推理**——优先启用 CSCD 多轮递归
3. **单轮协议（max_rounds=1）不建议作为默认配置**——存在空结果风险，且收益有限
4. **协议校验失败时应有 fallback**——输出原始模型响应而非空结果
